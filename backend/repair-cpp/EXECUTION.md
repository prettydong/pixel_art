# Repair solver execution boundary

`dev.hpp` is generated by the architecture-coding agent.  The backend snapshots it with the trusted `model.hpp`, `repair_most.hpp`, and `main.cpp`, compiles the snapshot, and runs `repair-solver input.txt result.jsonl`.

The runner validates the binary wafer, its layout, fail count, and synthetic flag against the database dataset before converting it to `PIXEL_REPAIR_INPUT_V1`. It records SHA-256 hashes for the wafer, generated text input, `dev.hpp`, and all three trusted core sources. It refuses changed source or snapshot files after execution, limits time and output, checks `result.jsonl` against a 256 MiB limit, and (when Linux `prlimit` exists) enforces address space, CPU, and file size limits. Files already generated are retained on failure; early preparation failures may precede the manifest or logs.

The backend starts `scripts/repair-supervisor.mjs` with an IPC channel in its own process group. Compiler and solver children inherit that group. The supervisor kills the group if the backend disconnects; the backend also kills the group on cancellation and after process completion. Deliberately detached programs are outside this cooperative process-tree contract.

This is an execution control, not a security sandbox. The coding agent can write arbitrary C++ and runs under the same Pi service account as the application. In particular, `prlimit` does not isolate filesystem access, network access, process namespaces, or credentials inherited from the host. Core resource-model validation belongs in the trusted C++ templates and in the Node-side input and result checks; it cannot prove that agent-authored redundancy selection is safe or correct.

The solver must print JSONL progress records to stdout and exactly one `summary` record, and write its detailed result to `result.jsonl`. A nonzero exit, malformed output, inconsistent yield/counts, timeout, cancellation, changed snapshots, or missing compiler fails the job while keeping the directory for review/download.
